# ONE BOX technology adoption roadmap

Status: planning synthesis. This document does not authorize dependency changes or implementation.

E0 through E8 are draft operating-environment decomposition labels only. They are not an accepted implementation sequence, backlog, or source of retained-code authority.

## Outcome

Keep ONE BOX as the base and introduce outside technology only when a named product phase needs it, its license is clear, and it preserves the Page IR and release authority chain.

## Sequence

### T0, protect authority and close legal stops

- Preserve the run's immutable layout authority. `page-ir-v1` owns validated IR and typed mutation; `template-v1` retains the existing guarded compiled-site mutation path. They never merge or switch within a run. Candidate identity remains the unit of review, qualification, and release.
- Keep every retained Electron/native/remote-content shell and the embedded browser at `REJECT / NOT_AUTHORIZED` until a rewritten browser plan closes EB-001 through EB-021, beginning with hostile-page isolation and fail-closed behavior. Each finding needs an owner, threat, deterministic oracle, fixture, exit gate, and retained-code boundary.
- Keep A4 visual motion authoring blocked until ONE BOX obtains written GSAP consent or accepts a Motion/non-GSAP evaluate-and-replace plan with a deterministic oracle and removal path. Existing deterministic and reduced-motion runtime behavior is not motion-builder authorization.
- Fail closed on mixed, custom, missing-SPDX, Commons Clause, AGPL, and GPL candidates.

Exit: authority register is accepted for the next implementation plan, browser P0/P1 issues have current evidence, and every selected dependency has an owner, version, license receipt, and removal plan.

### T1, build research and benchmark infrastructure

- Create the pinned offline visual-understanding corpus.
- Add Apple-silicon measurements for Qwen3.5-4B, PaddleOCR-VL, Florence-2, SigLIP2, Qwen embeddings, and optional later specialists.
- Include ScreenSpot-v2, ScreenSpot-Pro, WebClick, pattern2code, and reviewed Design2Code cases.
- Adapt ST-WebAgentBench's 80 modality-challenge and policy patterns into rights-reviewed local fixtures. Keep the official benchmark outside the offline corpus; run it only through a separately authorized, sandboxed integration after environment, credential, setup-script, effect, and dependency review.
- Add hostile-content fixtures before any browser-linked model evaluation.
- Prototype Puck interaction patterns and research Motion requirements against synthetic fixtures only; these reports do not clear the A4 visual motion-authoring stop.
- Run any pre-authorization Electron Forge packaging, signing, notarization, and update experiment in a disposable out-of-tree spike with no remote content. Retain reports and receipts only, not application shell code.
- The pinned Deep Agents JavaScript SDK completed its disposable out-of-tree synthetic job-plane spike under OBX-P180. T1 through T11 passed and application package/lock hashes stayed unchanged, but no material advantage was demonstrated; the baseline comparison remains architectural rather than same-fixture performance evidence. The decision is `adapt-patterns-only`: retain the ONE BOX controller and import no runtime dependency. This separate candidate does not change the cataloged Python `deepagents` row.

Exit: capability-specific thresholds are declared; benchmark inputs are rights-reviewed and hashed; results include cold start, p50/p95, unified memory, disk, energy, output drift, and attempted egress.

This research lane may proceed before product implementation because its outputs are reports and fixtures, not production candidate mutations.

### T2, website authority and Canvas foundation

Complete the existing A0 through A3 and P1 through P2 track before adding a subsystem that could mutate or release a site. Deterministic static Page IR is the only Phase 1 production compiler/document authority. The existing `template-v1` path remains a closed compatibility path under the authority register, not a target to extend:

- A0: freeze authority and supersession.
- A1/P1: lifecycle foundation.
- A2: Page IR candidate path and immutable layout authority.
- A3/P2: typed Canvas mutation and approval automation.

Retain Tailwind as a pinned compile dependency, the AI SDK as the existing routing surface, Playwright and axe as gates, and Monaco only for trusted drafts, receipts, and diffs.

Exit: every edit reaches a new candidate only through typed apply, deterministic compile, gates, and explicit promotion.

### T3, Canvas capability slices and operating-environment research

- A4: selection, responsive comparison, assets, hierarchy, history, diff, restore, and quality navigation; visual motion authoring remains subject to the T0 stop.
- E0: identity, role, membership, and sync contracts only; no desktop or native shell.
- E1: model registry, provider drivers, per-turn model and effort switching, context hashes, receipts, budgets, and compare mode.
- E2: skills, slash commands, Plan, source-linked PRDs, tasks, and schedules.
- E3: comments, presence, optional cursors, draft co-editing, and signed activity events.

E0 through E3 remain draft decomposition and research/pattern notes. A separately accepted operating-environment specification and implementation plan are required before retained work. No retained shell or remote-content host can be smuggled through E0 while the browser stop remains open.

Adopt or adapt here:

- provider and receipt contracts from t3code;
- bounded loop state from loop.js;
- capability-middleware ideas learned from the Python `deepagents` source;
- delegation, interruption, and nested-stream contract ideas from the completed JavaScript Deep Agents spike; the runtime was not selected, and E1 Agent Studio, route policy, memory, project state, approvals, and release remain ONE BOX-native;
- Monaco for trusted plan/code/diff surfaces;
- Yjs for draft PRDs, notes, comments, cursors, and awareness only;
- signed actor/event envelopes inspired by Buzz;
- Puck interaction experiments only if they compile back through Page IR.

Exit: model and skill output remains a typed proposal; shared Page IR changes serialize or conflict explicitly; no CRDT merges site authority or approvals.

### T4, embedded browser rewrite gate

The rejected E4.0 through E4.7 sequence has no authority and is not reproduced by this roadmap. Do not reuse that numbering until a replacement browser plan is accepted.

Before any retained work, the rewritten plan must map every EB-001 through EB-021 finding to its owner, threat, deterministic oracle, fixture, exit gate, and retained-code boundary, then pass the required human and independent reviews. Until then, Electron, other native shells, `WebContentsView`, remote content, browser profiles, CDP adapters, capture bridges, packaging integration, and updaters remain blocked. Only disposable out-of-tree spikes that retain reports and receipts rather than application code may proceed.

If the replacement plan is accepted, it will define the new decomposition and technology choices; this roadmap will link to that accepted sequence rather than restating it.

Exit: the rewritten plan is accepted with all EB findings closed on current evidence. That planning exit is necessary but does not itself authorize implementation.

### T5, client room and post-Phase-1 stack research

- Complete P3 before E6. LiveKit adds media transport only after the P3 review-origin threat model, scoped-session, invitation, candidate-lock, revocation, stale-approval gates, and exit criteria pass.
- E6: LiveKit room, screen share without remote control, exact-candidate review, source-linked transcript decisions, and short-lived guest access, subordinate to the P3 candidate and review contracts.
- Phase 1 has one production target: deterministic static compilation from Page IR. React and Next.js are not alternate Phase 1 site document or compiler authorities.
- E7 is a draft post-Phase-1 research label. React targets and signed `ExperienceModule`s may be considered only after Phase 1 exits and a separate schema/security ADR and implementation plan are accepted. The later contract must include signed manifests, fixed allowlists, CSP, network permissions, SSR/static fallback, reduced motion, accessibility, performance, SEO, ownership, update, revocation, and removal rules.
- Evaluate Motion only inside the A4 license/capability decision; research does not clear the visual motion-authoring stop.
- React Three Fiber, GSAP, WebGL, and other executable premium behavior remain deferred to that later module decision. A future module may add bounded behavior but cannot author the site document, bypass Page IR or release gates, or release itself.

Exit: P3 has passed before E6 media transport. Any post-Phase-1 stack proposal has its own accepted schema/security authority; Phase 1 remains portable static Page IR.

### T6, agency qualification, publishing, and team delivery

Continue the approved P4 through P8 sequence:

- P4: agency qualification and evidence-backed SEO.
- P5: release orchestrator and conformance provider.
- P6: separately selected and authorized production provider.
- P7: separately accepted appointment integration.
- P8: end-to-end qualification and owner-approved rollout.

Use Lighthouse, axe, schema-dts, Playwright, visual-baseline receipts, and resumable audit patterns as subordinate workers. Adapt the Instatic publish protocol in P5/E8 only after P1, P3, P4, and explicit P5 implementation authorization; it remains subordinate to the Release Orchestrator and gains no E7 publishing authority. Electron Forge may enter retained work only after the rewritten EB-001 through EB-021 browser plan passes, the target-topology decision selects a native shell, and the signed/notarized updater spike passes. Evaluate deployment adapters only after the owner selects the production provider.

Exit: the exact locked candidate passes deterministic, rendered, human, security, SEO, accessibility, recovery, and provider conformance gates; the release is atomic and rollback-capable; the desktop build is signed, notarized, and safely updatable on every agency Mac.

## Adoption record required for every dependency

Each implementation plan must record:

1. exact package, repository, version, commit or model revision;
2. license and notices, including transitive or bundled model terms;
3. phase and capability owner;
4. input and output contract;
5. data, network, secret, and filesystem permissions;
6. failure mode and fail-closed behavior;
7. deterministic oracle or benchmark threshold;
8. provenance and runtime receipt;
9. upgrade policy and removal path;
10. why the dependency cannot become a second source of truth.
