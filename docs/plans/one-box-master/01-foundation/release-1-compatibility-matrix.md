> Planning-only companion to [the Release 1 contract](release-1-contract.md). It defines the environments and version boundaries Release 1 must support. It does not select a provider, add dependencies, authorize implementation, or establish numeric quality targets.

## Reading the matrix

- **Required** means a Release 1 exit condition, not a promise that the current checkout already satisfies it.
- **Compatible** means the environment may consume the same immutable, hash-bound artifact without becoming a second source of truth.
- **Deferred** means the capability belongs to a later contract and must not be smuggled into Release 1 through a dependency or convenience integration.
- Performance and quality cells intentionally use a baseline protocol rather than invented thresholds. A target can be proposed only after the protocol in the Release 1 contract is frozen and run.

## Required compatibility evidence before Release 1 exit

The packet is not complete until the implementation plan names concrete fixtures and receipts for:

1. both admitted source-authority paths or an explicit reason one is excluded from the first fixture corpus;
2. one candidate through Canvas mutation/history/restore and named-human visual review, client review, changes requested, client lock, qualification, release approval, deployment verification, healthy monitor, failure, rollback, and re-delivery;
3. stale revision, stale candidate, mismatched hash, unknown version, adapter timeout, unknown provider state, and monitor-loss no-op behavior;
4. client-review revocation and no-mutation enforcement;
5. static bundle reproducibility plus secret/PII/executable-content scans across
   delivery artifacts, prompts, general logs, receipts, and manifests;
6. accessibility, SEO, and performance baseline records across every supported route;
7. append-only audit-lineage, deduplication, tamper, access, redaction, retention,
   rollback, and re-delivery evidence;
8. explicit evidence that no deferred browser, collaboration, media, appointment, or provider-specific technology becomes hidden Release 1 authority.

## Unresolved compatibility decisions

- The exact Apple-silicon OS/runtime/browser versions and supported client-review browser set must be frozen by the baseline protocol.
- The first admitted Page IR and template-v1 fixture corpus must be named before implementation authorization.
- The review-session transport/authentication mechanism remains an implementation choice until candidate scoping and revocation are proven.
- A concrete deployment provider remains unselected; its adapter cannot be inferred from this matrix.
- Monitor probes and the manual-operator boundary must be defined for the first authorized adapter.
- Numeric accessibility, SEO, and performance targets remain unset until baseline evidence is captured and reviewed.
