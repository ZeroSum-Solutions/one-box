# Local API threat model

one-box is a local-first, single-user workspace. Evidence records can include client-provided facts, source links, and run-relative screenshot paths, so its API boundary is intentionally narrower than a public web service.

- Every protected API method validates two authorities: the parsed request URL and the effective HTTP `Host`. Both hostnames must be exactly `localhost`, `127.0.0.1`, or `[::1]`, and their normalized ports must match. Suffix lookalikes, missing or malformed Host values, DNS-rebound public hostnames, and port mismatches are denied. The effective browser origin is the request URL protocol plus the validated Host authority. This permits a legitimate browser request when Next.js internally reconstructs `request.url` with a different loopback hostname, without trusting a public or lookalike Host. The site-preview route is intentionally unauthenticated, but the shipped `dev` and `start` commands bind the entire application only to `127.0.0.1`, so LAN exposure is outside the supported threat model. Browser mutations additionally require `Origin` to exactly equal that effective origin, an accepted non-simple content type, and `Sec-Fetch-Site: same-origin`. Cross-origin, missing-Origin, missing Host, port-mismatched, and missing Fetch Metadata browser mutations are denied before their bodies are consumed.
- Phase 1 production authorization is Website-only and does not weaken the local API guard. Mutation routes reject hostile origin or bearer state first, validate the applicable run ID and request shape, then load the persisted intake target before any model, provider, stage, repair-credit, or filesystem mutation work. Unsupported `web-app` and `ios-app` operations return `409` with code `unsupported-project-target` and direct the operator to start a new Website project. `/api/run` applies this check before opening its event stream; `runPipeline()` and `buildSite()` repeat it for direct internal callers.
- `ONE_BOX_API_TOKEN`, when set, is an additional bearer capability for non-browser clients on those loopback hosts and bypasses the browser Origin, Fetch Metadata, and content-type checks. It is never written into a URL, artifact, export, or model prompt.
- A safe GET/top-level browser navigation may omit `Origin`. This is accepted so local evidence pages and downloads work. Mutating non-browser clients must use the configured bearer. Access still requires a valid high-entropy run identifier and a listener on the local one-box origin. This is appropriate for the loopback-only threat model; deployment on a shared or public interface requires mandatory authentication at the reverse proxy or application layer.
- Chat authorization failures keep the submitted prompt and its exact target, research, upload metadata, and upload-session snapshot attached to the failed attempt. The default UI explains recovery without exposing protocol details; an optional disclosure includes the HTTP status. Retry reuses the snapshot and its validated UUID attempt ID. Before model or pipeline work, the server stores a canonical request fingerprint and a reserved run ID behind a cross-process filesystem claim. A completed repeat bypasses the model and returns that run; reuse with different input fails with `409`. Edit restores the prompt and settings. An expired upload-session claim remains non-retryable: its stale handle and metadata are cleared and the files must be selected again.
- Upload authorization runs before multipart parsing or staging. A `403` therefore reports a blocked local request, not invalid file selection. The browser retains the selected `File` objects in component memory when available, marks them `Not uploaded`, and offers an in-place retry; those objects disappear on navigation or unmount and are never persisted by this recovery UI. Every selected batch also carries a high-entropy UUID request ID. The private session manifest stores only its hash, the batch fingerprint, and the resulting file IDs, so an exact replay returns the original metadata while reuse for different bytes fails with `409`. Validation failures may instead ask the user to adjust type, size, archive safety, or count. A `401` preserves the existing upload-expiry behavior by clearing stale staged metadata and requiring a fresh selection.
- Exports contain versioned JSON payloads, hashes, source links, and run-relative artifact paths. They do not embed Refero media bytes or uploaded file bytes.
- Refero images are accepted only as PNG, JPEG, or WebP when the declared MIME exactly matches the file signature. Remote responses are streamed through a 1.5 MB per-image cap even without `Content-Length`; MCP base64 is size-checked before decode; and one run may retain at most 4 MB of Refero image evidence. Rejected bytes never reach disk or a model prompt.
- Evidence version creation, contract lint/export, workflow mutation, and approved-alias promotion share one per-run transaction lock. A failed multi-file promotion restores prior aliases and removes newly written version files before releasing the lock.
- `POST /api/runs/<id>/fallback` uses the same local mutation guard before validating the path ID, consuming a body, or entering fallback persistence. The request body has no authority: the server supplies the closed `operator-requested-after-failure` reason and `createTemplateFallbackRun` requires an already-failed `page-ir-v1` source. The transaction creates or resumes one separately identified `template-v1` child, copies only verified intake/uploads, links both runs, and never changes or deletes the source authority, Page IR, failed candidate, evidence, or live-site artifacts. Missing sources return a stable `404`; closed fallback precondition conflicts return `409`; unexpected failures return a stable `500` message without reflecting internal exception text.
- Uploaded text sent to a model is type-gated, UTF-8 decoded, control-character stripped, credential-pattern redacted, capped per file and per run, and excludes original names, IDs, hashes, storage paths, and upload-session handles. Binary and unsupported uploads are recorded as unsupported rather than silently parsed or represented as consumed assets.
- `POST /api/edit`'s `referenceAssetId` (canvas-upgrade B3, chat reference attachment) is an id-shaped string (length-bounded, matching the existing `sourceAssetId` convention in `src/lib/imageLibrary.ts`), never a URL and never trusted on its own. It is resolved against the REQUESTING RUN's own image library (`listProjectImages(runId)`) before it can reach a model prompt; an id absent from that run's own library, or not yet `completed`, is rejected before any generation call. It is only ever dereferenced to that item's own previously-generated prompt text — never to arbitrary bytes, a cross-run id, or a client-supplied URL — so it cannot trigger a fetch of attacker-controlled content.
- `POST /api/assistant/<id>`'s `scopeEditId` (canvas-upgrade Wave 6, Play 5, selection-scoped assistant references) is an optional editId, format-checked at the zod boundary with the same `editId` shape enforced everywhere else one crosses a boundary (`elementEditor.ts`, `imageLibrary.ts`, `siteMotion.ts`), never trusted on its own. Whether it actually names something can only be known once the site HTML is loaded, so `runAssistantTurn` re-validates the format (defense in depth for direct, non-HTTP callers) and then resolves it against THIS run's own live `data-edit-id` inventory; an id absent from that inventory is rejected before the owner's turn is persisted or any model call is made. Every `suggestions[].editId` the model returns is constrained to the same run-time-computed scope — the element itself or a real descendant walked through the live parent chain, never an id-prefix guess — by restricting the response schema's own `editId` enum to that subtree, so an out-of-scope suggestion is a schema violation handled by the existing retry-then-safe-fallback path, not a second bespoke filter.
